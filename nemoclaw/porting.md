# NemoClaw (OpenClaw) + Hermes Agent — PCAI port

Ports **NVIDIA NemoClaw / OpenClaw** (an always-on AI-agent gateway) **and
Hermes Agent (Nous Research)** to HPE Private Cloud AI (PCAI) as a BYOA Helm
import. One chart, one agent per pod, selected by `agent: openclaw` (default)
or `agent: hermes`. Both agents share the same LiteLLM endpoint and the same
optional Telegram channel.

## Layout

| Path | Purpose |
|------|---------|
| `logo.png` | Logo shown in the PCAI portal during import. |
| `0.2.5/` | Current Helm chart (version folder). |
| `nemoclaw-0.2.5.tgz` | Importable Helm package of the `0.2.5` folder. |
| `porting.md` | This file. |

Rebuild the package with `helm package 0.2.5 -d .`.

## What the chart does

A single-gateway sandbox app exposed on the PCAI Istio `ezaf-gateway` as
`https://<release-name>.<your-pcai-domain>` (an Istio `VirtualService`), with:

- **Agent selector** — `agent: openclaw` (NemoClaw/OpenClaw gateway) or
  `agent: hermes` (Hermes Agent). Exactly one agent container per pod; the
  chart renders different ConfigMaps, Secrets, and Services per agent.
- **OpenClaw path**: static dashboard URL + static gateway token baked at
  import time (no post-deploy scrape). The token is entered in the values
  form (`gateway.token`) or generated by the PCAI portal.
- **Hermes path**: Hermes Agent with an OpenAI-compatible API on port 8642
  and a web dashboard on port 18790 (same VirtualService host). The API
  server key (`hermes.apiServerKey`) and dashboard basic-auth password
  (`hermes.dashboardAuth.password`) are baked at import time; the chart
  seeds `~/.hermes/config.yaml` + `.env` from a ConfigMap at pod start.
- **LLM**: a single explicit `litellm.baseUrl` input — the full URL of either
  a LiteLLM proxy or a direct OpenAI-compatible model endpoint. No
  auto-detection, no fallback. `litellm.apiKey` is pasted directly into the
  portal values form and is never committed.
- **Telegram channel (optional)** — `telegram.enabled` + `telegram.botToken`
  register the channel for the selected agent. On each pod start a one-off
  validation (`files/telegram-verify.js`) runs before the gateway starts:
  `getMe` proves the token + outbound egress, then one test message is sent.
  It is bounded (20 s) and non-fatal, so it can never block the deploy.
- **Access control** — `telegram.allowAll` (default `true`) sets
  `dmPolicy`/`groupPolicy=open` + `allowFrom=["*"]` so anyone can use the bot.
- **Persistence** — `/sandbox/.openclaw` (OpenClaw) or `/sandbox/.hermes`
  (Hermes) on a 10Gi PVC.

## PCAI-specific adaptations

- **Domain / gateway**: exposed on the `ezaf-gateway` Istio gateway.
  `ezua.virtualService.endpoint` defaults to `${RELEASE_NAME}.${DOMAIN_NAME}`
  (PCAI platform placeholders substituted at import), so the host is fully
  dynamic and the chart works on any PCAI deployment with zero edits. To pin
  a host, override with a literal full host — the portal reads literals
  verbatim (only `${...}` placeholders are substituted, no `{{ }}` Helm
  expressions).
- **Distinct framework names** — the EzAppConfig label (portal app name) is
  per-agent (`NemoClaw (OpenClaw)` vs `Hermes Agent`), so both are
  distinguishable in the UI.
- **Release-scoped resource names** — with `fullnameOverride` empty, all
  resources are named from the release name, so two releases of this chart
  (e.g. `nemoclaw-openclaw` + `nemoclaw-hermes` side by side) own separate
  secrets, ConfigMaps, PVCs, services, and VirtualServices with no ownership
  collisions.
- **Istio sidecar**: the agent pod gets a sidecar (namespace
  `istio-injection: enabled`); the sidecar forwards `X-Forwarded-For`.
- **Memory / probes**: the OpenClaw gateway's V8 heap is capped by the
  container memory limit (~521MB at 1Gi); a Telegram long-poll pushes it
  past that, so OpenClaw uses **2Gi** limits. Hermes (Python) uses **4Gi** —
  its boot loads ~50 plugins from NFS and dashboard + gateway + Telegram
  long-poll need more headroom. Both deployments use a **300 s liveness
  initial delay** so the slow NFS boot is not killed by the probe.
- **One Telegram bot token per deployment** — Telegram allows a single
  long-poll `getUpdates` per token; two deployments sharing a token collide
  and the losing gateway tears down. Use a distinct bot per agent runtime.

## Deploy (via the PCAI portal — no kubectl)

1. **PCAI portal → Applications → Import / Deploy** (BYOA flow).
2. **Point it at this framework** — upload `nemoclaw-0.2.5.tgz` (the portal
   also picks up `logo.png` and `porting.md`).
3. **Fill in the values** in the portal values form:
   - `agent` — `openclaw` (default) or `hermes`.
   - `litellm.baseUrl` — full URL of the LLM endpoint (required).
   - `litellm.apiKey` — LiteLLM / model API key (required; never committed).
   - `litellm.model` — model name as registered at the endpoint.
   - `gateway.token` (openclaw) — dashboard token, >= 16 chars.
   - `hermes.apiServerKey` + `hermes.dashboardAuth.password` (hermes).
   - `ezua.virtualService.endpoint` — for the "Open" button; the default
     `${RELEASE_NAME}.${DOMAIN_NAME}` works on any deployment.
   - Optional `telegram.*` (a distinct bot token per deployment).
4. **Deploy** — the portal shows install progress, then a **ready** health
   state plus the dashboard URL and an "Open" button.

The import is idempotent — re-running it re-applies the values and
re-deploys.

## Verification (via the PCAI portal — no kubectl)

1. **App health** — Applications → the app → status **ready**; the Logs tab
   shows the agent logs.
2. **Dashboard** — click "Open".
   - OpenClaw: **Health OK** + working **Chat** section.
   - Hermes: web dashboard with model routing + chat (`admin` + the pinned
     password).
3. **Telegram channel** (if enabled) — the bot sends a one-off test message
   on first deploy (after you `/start` it); afterwards it replies to DMs /
   group messages. A pairing code means `telegram.allowAll` is `false` — set
   it to `true` and re-deploy.
